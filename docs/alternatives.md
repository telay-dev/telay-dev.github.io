# 复用边界与命名方向

本轮是项目工程选型对照，不是穷尽所有产品的市场调研。网页连接入口仍是主产物；不变更网络协议或未经批准替换底层。

## 已有相关能力

- Paseo 以编码代理编排为产品中心，提供可选端到端加密中继、本地网络直连和自行配置隧道。它可以覆盖远程操作编码代理的诉求，但不是“保留任意本地网页原界面”的同一种入口。后一项是对产品定位的判断，不是证明其所有扩展方式均不可能实现。::cite[20]
- Tailcat 是不依赖 Tailscale 控制面的连接底座，官方浏览器入口仍标注实验性质；官网示例以文件/文本互通为主。我们已经复用了它，不应再写自己的加密与中继底座。::cite[1]
- Cloudflare Tunnel 通过 cloudflared 发起的出站连接把网络内资源连接到 Cloudflare，再交给客户端访问。适合直接发布本地 HTTP 服务；其默认路径并非我们当前页面与设备之间的局域网 WebRTC 直连。::cite[202]
- Tailscale Funnel 通过 TCP 代理与 Funnel relay 把本地资源发布为公网 URL。它也是免自建公网网关的候选路径，但需要遵循其产品配置与使用边界。::cite[170]
- Service Worker 截获 HTTP、经 WebRTC 访问 NAT 后的设备、对上游 HTML 副本注入适配的思路不是新发明。SequentialRead 的原作者文章描述了同类设计，也明确记述原型进展；这篇文章本身不能证明当前已有能直接替换我们的成熟完整产品。::cite[189]

## 工程判断

如果目标只是“远程打开本地网页”，应优先实测现成 Tunnel/Funnel，而不是扩大本项目的代理实现范围。如果必须同时满足无浏览器插件、不改变外部应用源码、内网直连优先、静态入口部署、轻量配对，我们目前仍有一个集成层需要维护。

现有代码只支持固定 loopback HTTP 上游及同源 WebSocket，对 SSE、长流、外部应用自己的 Service Worker 等有限制。它不能被描述为任意网页的透明代理，也不能因为使用公共中继就承诺无限带宽、商业可用性或 SLA。

Cloudflare Tunnel 的 WebSocket 支持可由官方 FAQ 核实。::cite[204]

Quick Tunnel 明确不支持 SSE，不应把演示路径和正式隧道的能力混为一谈。::cite[198]

## 命名方向

产品名与实现脱钩：不绑定 DeepSeek、Tailcat 或“必须走中继”的 Relay。推荐中文方向“近径”，英文先将 Nearlane 作为表达“通向自己的设备”的候选，而非已获许可的商标。

初步检索已见 Nearlane 的零售商业用途，因此本轮不直接改品牌、不购买或声称可注册域名。正式选名仍需单独核验商标、域名及包名。::cite[226]
